# 실험 기록: 전환 정의 변경 (postback tier → 몰 IP 매칭) 1차 백테스트

날짜: 2026-07-09. 관련 코드/쿼리: [`querys/addi_conv/`](../../querys/addi_conv/),
[`README.md`](../../README.md) §2-5, `evaluation/backtest.py`(`cumulative_topk_summary`).

## 배경

기존 프로젝트는 "전환율"을 `(bid log 유저 중 postback 발생 유저) / (bid log 유저)`로 봤다
(백테스트 라벨 = postback tier T2+ 도달 여부). 이걸 한 단계 더 엄격하게, "postback이 발생한
유저 중 실제로 광고주 몰(`"prod_addi_conv".raw_conv_web`/`raw_conv_web_imp`)의 `mall_ip`와
매칭되는 유저 비율"로 바꾸는 걸 검토했다 — postback(광고 자체의 반응 트래킹)과 실제 몰
방문/구매(광고주 쪽 트래킹)를 구분해서 보자는 목적.

## 1. 스키마/매칭 신뢰도 진단

이 저장소는 `raw_conv_web(_imp)`를 조회한 적이 없어 컬럼조차 몰랐다. 진단 쿼리
(`querys/addi_conv/_archived/00~08`, 결론은 [`querys/addi_conv/README.md`](../../querys/addi_conv/README.md)에
정리)로 확인한 내용:

- **postback_log의 ip 필드는 신뢰할 만함**: 결측 0.001%, IPv4 포맷 100%, `ip`≈`request_ip`
  (98.4% 일치), IP 하나당 distinct ifa 중앙값 1(p99=2, 최대 6) — 공유 IP/NAT로 인한 오매칭
  위험이 우려보다 작음.
- **raw_conv_web(_imp) 스키마**: `cmp_no, pid, ev, mall_dt, post_datetime, mall_datetime,
  mall_ip, cate` + year/month/day 파티션. `post_datetime`은 `mall_datetime`과 무관하게 튀는
  값이라(같은 mall_dt 안에서도 몇 달씩 차이) 신뢰 불가 — 매칭에는 `mall_datetime`만 사용.
- **`pid`는 유저 식별자가 아니다**: cmp_no당 distinct pid = 1(14개 cmp_no 전부 확인) — 캠페인당
  고정 픽셀/게시물 토큰. 유저 단위로 조인할 수 있는 키는 `mall_ip`뿐.
- **`cmp_no`는 addi 캠페인과 같은 ID 체계**: postback의 22개 cmp_no 중 13개(93%)가
  raw_conv_web(_imp)의 14개 cmp_no와 겹침. → `mall_ip` 단독보다 `mall_ip + cmp_no`가 더
  정밀한 매칭 키.
- **ev(이벤트 타입) 분포**: 99.95%가 `page_view`(몰 방문), `order`(실구매)는 두 테이블 합쳐
  전체 60건뿐(매칭 이전 수치). **order만 전환으로 인정하면 매칭 후 양성이 사실상 0으로
  수렴** — 사용자 확인 후 "몰 방문(page_view 포함 전체 ev)"을 전환으로 채택.

## 2. 절대 매칭 건수 (핵심 제약)

시간창(24h/72h/7일/30일/무제한) × cmp_no 요구 여부를 조합해 확인 (`08`, 4~5월 기준
postback 유저 564,492명 중):

| 조건 | 매칭 유저 | 비율 |
|---|---:|---:|
| IP만, 무제한 시간창 | 680 | 0.120% |
| IP만, 30일 | 308 | 0.055% |
| IP+cmp_no, 무제한 시간창 | 412 | 0.073% |
| IP+cmp_no, 30일 | 173 | 0.031% |
| IP+cmp_no, 7일 | 47 | 0.008% |

절대 건수가 매우 작다. 6월(더 짧은 관측 기간이라 전환이 쌓일 시간이 부족 — right-censoring)
기준으로는 postback 유저 303,554명 중 IP만 170명(0.056%), IP+cmp_no 30명(0.0099%).

**재학습 시 문제**: 학습 pool(`user_profile_apr_may.csv`)은 5% 샘플이라, 4~5월 매칭 유저
412명(IP+cmp_no) 중 실제 pool에 들어있는 사람은 대략 20명 수준일 것으로 추정 — 이대로는
재학습이 사실상 불가능하다. (해결 방향은 "다음 단계" 참고, 아직 미착수.)

## 3. 1차 백테스트 (재학습 없이, 기존 T2+ 시드 모델로 검증)

재학습에 시간을 쓰기 전에, 기존 모델 점수가 새 전환 정의와도 상관관계가 있는지부터 저비용
으로 확인했다 — 재학습이 필요한지 자체를 판단하는 목적.

**주의(중간 실수)**: 처음에는 기존 스코어 파일(`supervised_lookalike_scored_jun.csv`,
11,729명 — "아직 postback 없는 신규 유저" 룩어라이크 후보군)에 새 라벨을 그대로 붙여 검증
했는데, 이 모집단은 정의상 postback 유저와 거의 겹치지 않아 양성이 0~1건만 나왔다.
사용자가 요청한 "전체 postback 유저" 모집단(303,554명)을 다시 스코어링해서 재검증했다.

### 실행

```
querys/addi_conv/10,11 실행 (postback 유저 전원 프로필/미디어 방문, 신규 유저 제한·샘플링 없음)
→ inference.user_profile / inference.media_sequence (기존 학습 모델 재사용)
→ scoring.infer_supervised_lookalike (기존 fusion_classifier_addi 재사용, 재학습 없음)
→ evaluation.backtest --label-col conv_matched_ip_any_cmp_any_window (IP만 매칭, 170명 기준)
```

- 프로필 임베딩 284,940명 → 미디어 임베딩 280,478명 → 최종 스코어링 269,914명(교집합).
- 라벨 매칭 최종 156명(0.058%) — 원래 170명에서 프로필/미디어 둘 다 있는 유저로 좁혀지며 감소.

## 해석

- **하위권은 뚜렷하게 걸러진다**: 1~3구간(하위 30%)이 일관되게 평균의 0.58~0.64배 — 이
  모델이 "전혀 반응 안 할 사람"을 가려내는 능력은 새 라벨에도 어느 정도 이전된다.
- **상위권 순위는 깨끗하지 않다**: 8구간(1.47×)이 10구간(1.28×)보다 높음 — 원래 T2+ 기준
  백테스트(상위 10% 1.7×, `docs/output_analysis.md`)보다 뚜렷이 약하고 단조 증가하지 않는다.
- 원인은 예상된 것: 이 모델은 T2+ 시드로 학습됐지 이 새 라벨을 목표로 학습된 적이 없고,
  양성 표본(156건)이 작아 추정 오차 자체가 크다.
- 결론: "완전히 무의미하진 않다"는 최소 신호는 확인됨 — 재학습을 시도해볼 가치가 있다는
  판단으로 다음 단계 진행.

## 다음 단계 (미착수)

1. **재학습용 시드 SQL**: `03_seed_interested_users_apr_may.sql`을 T2+ tier 조건 대신
   "postback 유저 중 IP(+cmp_no) 매칭" 유저로 완전히 대체.
2. **5% 샘플링 문제 해결**: 학습 pool이 5% 샘플이라 양성이 너무 준다(412명 → 추정 ~20명).
   매칭된 유저만 별도로 전수 조회해서(5% 샘플과 무관하게) pool에 강제 포함시키는 쿼리 추가
   필요 — 음성은 5% 유지, 양성은 100% 포함하는 stratified 방식.
3. **불균형 처리**: 양성 비율이 극단적으로 낮음(0.01~0.17% 수준) — 기존 `pos_weight` 방식만
   으로 충분한지 재검토. 랭킹(top-K% lift) 목적이면 calibration은 불필요하므로, 모델 선택
   기준을 val AUC 대신 PR-AUC/top-K lift로 바꾸는 쪽을 우선 검토.
4. 재학습 후 같은 방식(§2-5)으로 백테스트 재실행, 이 문서의 수치와 비교.
