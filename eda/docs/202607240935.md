# 실험 기록: propfit 소스 피처 설계 검토 (bid log 교체 + gender/age/segments 커버리지 실측)

날짜: 2026-07-24. 관련 코드/쿼리: [`seed/queries/lib/`](../../seed/queries/lib/), [`eda/queries/`](../queries/).

## 배경

기존 파이프라인(`querys/pipeline/`)은 addi(`addi_bid_log_flatten`, CTV 전용) 데이터만 썼다.
사용자가 다음 4가지를 검토해달라고 요청했다: (1) bid log를 propfit 계열 데이터로 교체,
(2) 유저 프로필에 gender/age 추가, (3) 미디어 피처에서 app_storeurl/genre 확인, (4) 세그먼트
데이터를 BERT류 임베딩에 쓸 수 있는지 검토. 라벨/지도학습 재구성은 이번 스코프 밖 — 피처
설계와 소스 데이터 커버리지 검증까지만 다룬다.

## 1. 소스 교체: bid log

`propfit.ab_bid_log_etl`(propfit 자체 bid log 샘플)로 시작했으나, `req_ext_allow_user_data_collection`
(데이터수집 동의) 컴플라이언스 컬럼이 없어서 addi와 동일한 컴플라이언스 필터를 온전히 걸
수 없었다. 이후 사용자가 `"prod-ptbwa-dw"."abi_bid_log_flatten"`(addi_bid_log_flatten의
형제 테이블, CLAUDE.md에 존재가 이미 기록돼 있던 웹+앱 인벤토리 테이블)로 바꿀 것을 요청 —
이 테이블엔 동의 컬럼이 실제로 있어 addi와 동일하게 동의+LMT 필터를 온전히 쓸 수 있다.
학습 기간 자리표시자(2026-04~05)로 걸었을 때 실측 72,254,582명(distinct device_ifa)이 나와
해당 기간 데이터 존재는 확인됐다(의도한 기간인지는 별도 확인 필요).

genre 관련: `app_content_genre`/`site_content_genre`가 샘플에서 전부 비어 있어(addi와 반대
상황 — addi는 app_bundle이 통신사 앱 3종 고정이라 genre로 대체했는데 propfit/abi는 거꾸로
genre가 비고 app_bundle이 다양함) media_sequence 아이템은 `COALESCE(app_bundle, site_page)`로
정했다(웹+앱 인벤토리 둘 다 커버). `app_storeurl`은 패키지 링크일 뿐 카테고리 정보를 주지
않아 genre 대체재가 못 된다.

## 2. ID 공간 크로스워크 진단 (`00_id_mapping_check.sql`)

`"propfit"."ptbwa_skb"`가 `(uuid, platform_ad_id, ad_id)` 세 컬럼을 가진 크로스워크
테이블임을 발견. 컬럼명만 보면 `ptbwa_tg.uuid ↔ skb.uuid`, `skp.ad_id ↔ skb.ad_id`가
자연스러워 보였지만, 실측 결과는 반대였다:

| 매칭 | 결과 |
|---|---:|
| `skp.ad_id` ↔ `skb.ad_id` | 매칭 (수십억 건, fan-out 포함) |
| `skp.ad_id` ↔ `skb.platform_ad_id` | 66건 (노이즈) |
| `ptbwa_tg.uuid` ↔ `skb.uuid` | 0건 |
| `ptbwa_tg.uuid` ↔ `skb.platform_ad_id` | 424,718건 |

결론: **`skp.ad_id`는 `device_ifa`(=`abi_bid_log_flatten.device_ifa`, 사용자 제공 원본
쿼리 전제)와 곧바로 같은 공간**이라 크로스워크가 불필요하고, **`ptbwa_tg.uuid`는
`platform_ad_id` 공간**이라 `device_ifa → skb.ad_id → platform_ad_id → ptbwa_tg.uuid`
크로스워크가 필요하다. 같은 propfit DMP라도 테이블마다 쓰는 ID 공간이 달라 각각 확인이
필요했다.

## 3. 커버리지 실측 (`04_coverage_check.sql`, `05_segment_demographics_check.sql`)

bid log 모집단(72,254,582명, 2026-04~05, 컴플라이언스 필터 적용) 기준:

| 경로 | 도달 인원 | 비율 |
|---|---:|---:|
| bid log → skb 크로스워크 | 3,314,414 | 4.6% |
| bid log → skb → **ptbwa_tg**(gender/age) | **2,500** | **0.003%** |
| bid log ↔ **skp**(세그먼트 보유) | **15,552,864** | **21.8%** |
| bid log ↔ skp 성별(모델링) 세그먼트(26455~26458) | **8,868,480** | **12.3%** |

`ptbwa_tg`는 전체 테이블 기준으로도 `ptbwa_skb`와 424,718건만 매칭되는 작은 패널이라
(위 §2), gender_code/age_range뿐 아니라 app_category/product_category 등 이 테이블의
모든 컬럼이 똑같이 이 상한(bid 모집단 대비 0.6%)에 걸린다 — "일부만 보강"이 아니라 조인
전체가 사실상 무의미했다.

반면 `skp.segments`는 (a) bid 모집단의 21.8%를 커버하고, (b) 그 안에 로컬 참조 파일
`data/sample/세그먼트_카테고리.csv`(1,050행, Athena 테이블 아님)로 확인되는 "인구통계 >
성별(모델링)" 세그먼트(26455~26458)가 있어 gender 대용 신호를 bid 모집단의 12.3%
(ptbwa_tg 대비 ~3,500배)에 제공한다. age는 "인구통계 > 연령대"(10003~10009, 선언값,
모델링 변형 없음 — `세그먼트_카테고리.csv` 전체에서 인구통계 카테고리는 이 11개 ID가
전부)로 세그먼트 보유 모집단(53,341,243명) 대비 11.3%(6,022,896명) — bid 모집단 대비
정확한 교집합 비율은 별도 측정 안 했음(추정치로 제시하지 않음, 필요시 후속 쿼리로 측정).

## 4. 설계 결론

1. **bid log**: `abi_bid_log_flatten` 확정, 컴플라이언스 필터 온전 적용 가능.
2. **gender/age**: `ptbwa_tg` 조인은 폐기(`01_user_profile.sql`에서 제거) — 커버리지가
   무의미한 수준. 대신 `03_user_segments.sql`의 `segments`에서 성별(모델링)/연령대
   세그먼트를 파싱해 쓴다.
3. **미디어**: genre 없음, `app_bundle`/`site_page` 아이템 + `app_storeurl`은 카테고리
   매핑 없이는 보조 신호 불가.
4. **세그먼트 임베딩**: `skp.segments`가 opaque ID가 아니라 실제 한국어 카테고리 텍스트
   (`세그먼트_카테고리.csv`)를 가진 것으로 확인 — EmbeddingBag(ID 기반)과 사전학습
   한국어 문장임베딩(카테고리 경로 텍스트 기반) 둘 다 후보. 실험은 이번 스코프 밖.
