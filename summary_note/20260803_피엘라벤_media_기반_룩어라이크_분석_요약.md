# 피엘라벤 Seed 기반 media(방문 앱/사이트) 룩어라이크 분석 요약

## 0. 목표

[`20260731_피엘라벤_seed_룩어라이크_분석_요약.md`](20260731_피엘라벤_seed_룩어라이크_분석_요약.md)는
세그먼트(성별/연령대/거주/관심사) 데이터만으로 만든 결과였다. 이 문서는 그 후속으로, **광고
노출 로그에 남는 "방문 앱/사이트 이력"(media)만 갖고 같은 질문(피엘라벤 seed와 비슷한 사람
찾기)을 풀어본 결과**를 정리한다.

- **모집단(pool)**과 **seed**의 media 성향이 실제로 다른지(1, 2번)
- 그 차이를 이용해 **media 활동 기준으로 새로 뽑은 신규 후보**가 seed와 얼마나 닮았는지(3번)
- media 임베딩(SASRec) 모델 구조(4번)

를 다루고, 마지막에 이번 분석 중 발견된 **아직 원인이 밝혀지지 않은 데이터 이슈**(5번)를
별도로 남긴다 — 결론에 영향을 줄 수 있는 사항이라 후속 조사가 필요하다.

**media 데이터의 근본적 한계**: 세그먼트는 "성별/거주/관심사"처럼 사람이 읽을 수 있는
이름표가 붙어 있지만, media는 그냥 앱 패키지명(`com.cashwalk.cashwalk`)이나 URL 문자열이라
카테고리 분류 데이터가 없다. 그래서 이 문서의 "성향 분석"은 세그먼트 문서처럼 "관심사
그룹별 비율"이 아니라, **어떤 개별 앱을 얼마나 많은 사람이 방문했는지(방문자 비율)를 그룹간에
직접 비교**하는 방식으로 진행했다. 앱 이름은 필요한 경우 잘 알려진 앱 위주로 괄호에
설명을 덧붙였다(공식 분류 데이터는 아님).

   1~4위 앱(SKT 다이얼러/토스/카카오페이/후후)이 신규 후보에서 정확히 0명인 것은 "성향
   차이"로만 설명하기엔 너무 극단적이다(아래 참고).

## 4. 임베딩 아키텍처 (`embedding/media_sequence`, SASRec)

옛 addi 트랙의 SASRec 구조를 propfit 스키마로 이식한 것(`04b/05b/07b/07d_*_media.sql` 출력,
top500 미디어 방문 이벤트 시퀀스, 30분 재방문 dedup 이미 적용됨).

```
media(아이템)              → nn.Embedding(vocab≤500, 64) ─────────────┐
position(순서)             → nn.Embedding(max_len=50, 64) ────────────┤
inventory_type/ad_type/    → 각각 nn.Embedding(64) ────────────────────┼─ sum → causal
  connection_type                                                     │  TransformerEncoder(2층, 2head)
                                                                        └─ → 마지막 실제 스텝의 hidden = z(64dim)
```

**다음-아이템(next-item) 예측**으로 라벨 없이 학습한다(SASRec 원 설계 그대로) — "지금까지
방문한 미디어 순서를 보고 다음에 방문할 미디어를 맞히는" 과제를 반복시켜서, 그 과정에서
생기는 z(64dim)가 "이 사람의 미디어 이용 습관"을 압축한 벡터가 되게 만드는 방식이다.

| 하이퍼파라미터 | 값 |
|---|---|
| vocab 크기 | ≤500(top500 미디어) |
| 임베딩 차원(z) | 64 |
| 최대 시퀀스 길이 | 50(최근 50 스텝만 사용, 넘으면 앞부분 자름) |
| 최소 시퀀스 길이 | **5** — 이보다 이벤트가 적은 디바이스는 학습/추론 모두에서 제외 |
| Transformer layer 수 / head 수 | 2 / 2 |
| FFN 차원 | 128 |
| dropout | 0.2 |
| batch size / epoch / lr | 128 / 30 / 1e-3 |

**학습 규모**: seed+pool+(구)후보를 합쳐 383만 3,720개 디바이스(seed 101만 5,872 + pool
253만 9,480 + 구 후보 27만 8,368)로 30 epoch 학습, loss 0.7645→0.5283로 단조 감소하며
안정적으로 수렴했다(중간에 좋아졌다 나빠지는 불안정 없음 — segment_features 학습이 겪었던
문제와 대조됨).

**전처리가 두 단계로 나뉘는 이유**: 이벤트 그레인 CSV(합치면 최대 14GB)를 pandas로 한 번에
못 읽어서, `build_features.py`가 청크 단위 스트리밍으로 2-pass(① vocab 적합 ② 디바이스별
시퀀스 인코딩) 처리해 `media_features.npz`로 압축한다. `--reuse-vocab` 옵션을 추가해(이번
신규 후보 처리에 사용) 이미 학습에 쓴 vocab을 그대로 불러와 재사용할 수 있게 했다 —
새 candidate 집단을 추가할 때 vocab이 달라지면 학습된 모델의 item 인덱스와 어긋나기
때문이다.

| (구)candidates_202606(segment 매칭, 66만 4,684명, `07a_candidate_profile.csv`) | 2026년 6월 | **87.80%**(대부분 한국) | **전부 0명** |
| candidates_202606_media_sample(이번 후보, 65만 9,893명) | 2026년 6월 | 확인 안 함(profile CSV 없음) | 전부 0명(캐시워크만 0.25%로 미미하게 존재) |
| seed(1번/2번 절) | 2026년 4~5월 | 98.38% | 44.06% / 23.81% / 6.66% / 4.79% |
| pool(1번 절) | 2026년 4~5월 | 31.59% | 8.47% / 3.73% / 0.78% / 1.67% |

**87.8%가 한국 지역인 (구)후보 집단에서도 이 4개 앱이 완전히 0명**이라는 게 핵심이다 —
지역 구성 차이로는 설명이 안 되고, **6월 파티션에서 이 4개 앱(또는 이들이 속한 특정
인벤토리/SDK군)의 `app_bundle` 값 자체가 사라졌거나 다른 값으로 바뀌었을 가능성**이
높아 보인다(예: 4~5월과 다른 패키지명/해시로 잡히거나, 해당 앱들이 6월 이후 이 인벤토리에서
빠졌거나, ETL/파티션 문제). 이 저장소에는 Athena 직접 조회 권한이 없어(CLAUDE.md 참고)
원인을 로컬에서 더 파고들 수 없다 — **다음 조회로 원인을 확인해야 한다**:

```sql
-- 예시: 6월 파티션에 이 4개 app_bundle이 정말 없는지, 값이 바뀌었는지 직접 확인
SELECT app_bundle, COUNT(*) 
FROM "prod-ptbwa-dw"."abi_bid_log_flatten"
WHERE year='2026' AND month='06'
  AND app_bundle IN ('com.skt.prod.dialer','viva.republica.toss','com.kakaopay.app','com.ktcs.whowho')
GROUP BY app_bundle;
```

**이 이슈가 확인되기 전까지는, 3번 절의 "신규 후보는 seed와 media 성향이 거의 안 겹친다"는
결론을 곧이곧대로 "media 신호가 약하다"로만 해석하면 안 된다** — 위 4개 앱이 6월에 정상
집계됐다면 겹침 정도(Jaccard 0.034)가 실제보다 훨씬 낮게 나왔을 가능성이 있다.
